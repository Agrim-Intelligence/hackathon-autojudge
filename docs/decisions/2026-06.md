## ADR-2026-06-05 · A reachable, rendered live URL is sub-`verified` UX/functional evidence

**Status:** accepted · **Date:** 2026-06-05 · **Deciders:** dev.ai@agrim.ai (Chetan), Claude
**Context driver:** submission `20260530-094253-chetan`; plan `docs/plans/eval-quality-fixes.md`

### Context

The repo invariant (root `CLAUDE.md`) says: *"Unverifiable ⇒ route to judge, never penalise.
Mark `insufficient`."* A working Streamlit dashboard (HTTP 200, hydrated past the SPA shell,
screenshots captured) was scoring `ux_polish = insufficient / null` because its two scripted
browser journeys ran out of step budget. Investigation (multi-agent workflow audit) showed the
scorer LLM only ever receives `browser.summary_for_scorer`, which collapses to the bare string
`"0/2 journeys succeeded."` — every positive render fact the verifier physically observed
(`page_title`, screenshots, per-journey `final_observation`, `live_url_reachable`) is discarded
at the prompt boundary. So "unverifiable" was being applied to a page the pipeline **did**
observe rendering. That is not absence of evidence; it is discarded evidence.

A tempting one-line fix — promote `insufficient→inferred` in `_clamp_kind` — was rejected: by the
time the clamp runs, `raw_score` is already `None` (the LLM never produced a number). Relabeling
a null does not create a score.

### Decision

1. **Render reachability is first-class, capped evidence.** When the live URL is reachable and
   the page rendered (`page_title` present, not auth-walled) but no journey completed, UX and
   functional may be scored `evidence_kind = inferred` (never `verified`), and the scorer is
   given the render facts to do so.
2. **`verified` stays grounded.** `_has_browser_success` (reachable AND a grounded journey
   success) remains the only gate to `verified` for functional/UX. Render-only never reaches
   `verified`.
3. **The ceiling is enforced in code, not prose.** Render-only UX carries a **deterministic
   hard cap of 7/10** (`cap_applied` + `cap_reason`), so the LLM cannot score a never-driven page
   highly. A grounded journey success lifts the cap.
4. **`insufficient` now means genuinely no evidence** — unreachable, credential-walled, or
   blank/non-rendering — aligning the verdict taxonomy with the invariant's *intent*.

### Consequences

- Fairer scores for the whole population of reachable-but-journey-incomplete submissions (common
  for Streamlit/SPA apps the browser agent can't fully drive). **This shifts anchor scores**, so
  `autojudge run-anchors` is a blocking pre-merge gate and `expected_total` is recalibrated with
  evidence per the calibration invariant.
- New text (`final_observation`) enters the scorer prompt → it passes through the existing
  `sanitize()` (anti-cheat: every untrusted channel sanitised before a reasoning model).
- No change to grounding, timeline/injection quarantine, or human-decision stickiness.

### Alternatives rejected

- *Promote `insufficient→inferred` in `_clamp_kind`* — cannot create a score from a null.
- *Keep `insufficient` + route to judge* — under-uses available evidence and, with minimal
  judges, floods the manual queue; contradicts the invariant's intent for an observed render.
- *Prompt-only cap* — advisory, not enforceable; violates "don't let the LLM claim above what the
  pipeline saw." Hence the deterministic value cap.

## ADR-2026-06-05 · Integrity flags must be accurate and styled by severity, not presence

**Status:** accepted · **Date:** 2026-06-05 · **Deciders:** dev.ai@agrim.ai (Chetan), Claude

### Context

For the same submission, the trace showed `"Large codebase (402K lines) … suggests possible bulk
import"` — LLM-authored speculation the `code_analyst` prompt forbids, over a value that is
actually a **byte** count (`line_count_estimate = sum(languages.values())`, GitHub Linguist
bytes) mislabeled as lines. The deterministic `"Zero commits inside hackathon window — submission
likely predates the event"` is accurate but cheat-flavored for a legitimately long-lived
org-private repo. The dashboard rendered **any** non-empty `integrity_flags` with quarantine-grade
alarm styling, and the flags feed the scoring LLM, so benign notes could depress a real score.

### Decision

- LLM-authored codebase-size / commit-ratio **speculation does not enter the integrity channel**;
  the deterministic layer owns commit signals.
- The bytes metric is **not labeled "lines"** to the LLM; large size with few commits is
  explicitly **not** evidence of import.
- Deterministic informational flags are **neutral, not accusatory** (keep the signal, drop the
  conclusion).
- Dashboard quarantine styling triggers on `verdict_effective == 'quarantined'` /
  `quarantine_cause:` — **not** `bool(flags)`. Genuine integrity signals
  (`future_timestamp:`, `duplicate_artifact:`, `prompt_injection_severity=`) keep their own
  **warning** styling; only benign notes render under a neutral block.

### Consequences

- All real anti-cheat (timeline cheat, injection, duplicate) stays loud; benign notes stop
  biasing judges and the scorer. No deterministic integrity signal is removed; the quarantine
  enforcement path is untouched.

## ADR-2026-06-06 · Intake field contract and journey sanitization policy

**Status:** accepted · **Date:** 2026-06-06 · **Deciders:** dev.ai@agrim.ai (Chetan), Claude

### Context
Full field audit of the intake form revealed: (1) email is collected but not used in the
scoring pipeline — intentional, for post-event outreach; (2) CLI command / notebook path
are classification hints, not execution inputs — labels were misleading candidates; (3)
declared journey steps flow into the browser-planner LLM completely unsanitized, unlike
live-page text which goes through `guard.sanitize()`; (4) the planner prompt had no
domain restriction on `goto` actions.

### Decisions
- Email stays with a documented intent comment. Never fed to an agent or shown to judges.
- CLI command / notebook path are relabelled as "app-type hints" with help text making
  clear they are not executed.
- Declared journey text is sanitized via `guard.sanitize()` at two points: at intake
  (before store) and at browser_verifier prompt construction for `source="stated"` journeys.
  Inferred journeys (system-generated) skip the extra guard call for cost efficiency.
- A domain-restriction rule is added to `prompts/browser_planner.md`.
- Test credentials are shown as a "provided / not provided" badge on the judge detail view
  so judges can distinguish "credential-walled with no creds" from "creds provided but failed".

### Consequences
- Anti-cheat invariant extended: all candidate-authored text channels are now sanitized
  before any reasoning LLM sees them.
- No pipeline behaviour change for valid, injection-free journeys.
- Judges can now distinguish the two credential-walled failure modes from the dashboard.
